# مصفوفة قبول مراحل التطوير — معيار 8/10

## القاعدة الملزمة

لا تعتبر أي مرحلة مكتملة لمجرد ظهور شاشاتها أو نجاح البناء. لا تغلق المرحلة إلا إذا حصلت على **80 من 100 على الأقل (8/10)** وفق هذه المصفوفة، وحققت جميع البوابات الحرجة أدناه. يجب توثيق الدليل في تقرير القبول قبل الانتقال إلى المرحلة التالية.

## أبعاد التقييم الموحدة

| البعد | الوزن | دليل القبول المطلوب |
|---|---:|---|
| الاكتمال الوظيفي | 20 | تنفيذ جميع حالات الاستخدام المعتمدة، بما في ذلك المسارات السلبية والاستثناءات. |
| التكامل والعلاقات | 20 | تدفق بيانات صحيح بين العقد، المشروع، BOQ، الجدول، التكاليف، المستندات والتقارير ضمن نطاق المرحلة. |
| الحوكمة والتدقيق | 15 | صلاحيات/حالات/اعتمادات/منع التعديل غير المسموح وسجل تدقيق بحسب نطاق المرحلة. |
| مصالحة البيانات والأرقام | 15 | مطابقة الأرقام مع بيانات القبول ومصادرها، مع تفسير مصدر كل رقم. |
| تجربة المستخدم والاستيراد | 10 | إدخال واستيراد واضحان، رسائل أخطاء قابلة للتنفيذ، وعدم فقدان السياق أو الصف الحالي. |
| الاختبارات الآلية واختبارات القبول | 20 | Unit + integration + E2E/قبول مناسبة، ناجحة وقابلة لإعادة التشغيل. |

## بوابات لا يمكن تجاوزها

- النتيجة الإجمالية: **80/100 أو أعلى**.
- لا يقل تقييم: التكامل، الحوكمة، مصالحة البيانات، أو الاختبارات عن **8/10**.
- لا توجد أخطاء حرجة مفتوحة في بيانات القبول أو ترحيل قاعدة البيانات أو مسار الإدخال الأساسي.
- يجب اجتياز سيناريو نجاح وسيناريو رفض لكل قاعدة حوكمة جديدة.
- يجب تشغيل الإنتاج Build واختبارات قاعدة البيانات، وتوثيق النتيجة والإصدار/نقطة الرجوع.
- لا تدخل بيانات قبول تجريبية إلى قاعدة المستخدم التشغيلية؛ تستخدم قاعدة أو بيانات اختبار معزولة.

## المرحلة A — نواة البيانات والاستيراد والحوكمة

**الهدف:** مصدر حقيقة موحد للعقد والمشروع وBOQ والجدول، واستيراد يمكن تدقيقه.

| البعد | شرط 8/10 للمرحلة A |
|---|---|
| وظيفي | Data Dictionary ملزم، نطاق مشروع/عقد واضح، ومركز استيراد يدعم المعاينة والتحقق والاعتماد أو الرفض. |
| تكامل | إنشاء/استيراد عقد رئيسي ينشئ نطاق المشروع الصحيح؛ عقد الباطن لا ينشئ مشروعًا ويظل تابعًا للعقد الرئيسي. |
| حوكمة | قواعد موحدة للكود، التاريخ، الكمية، الوحدة، العقد، الفترة، والتكرار تعمل في الإدخال والاستيراد والتعديل. |
| مصالحة | استيراد BOQ وXER وWIR في بيئة قبول يطابق عدد الصفوف والقيم والعلاقات مع ملف المصدر. |
| UX/استيراد | اختيار Sheet لملفات Excel متعددة الشيتات، معاينة الأخطاء، سياق مشروع/عقد ظاهر، ورسائل رفض دقيقة. |
| اختبارات | اختبارات نجاح/رفض للاستيراد الذري، النطاق، التكرار، الكمية، التواريخ، والترقية/النسخ الاحتياطي. |

## المرحلة B — التشغيل الفني: BOQ والبرنامج والكميات

**الهدف:** ربط معتمد بين BOQ وWBS والأنشطة والقياس والزمن.

| البعد | شرط 8/10 للمرحلة B |
|---|---|
| وظيفي | WBS وأنشطة ومستويات، علاقات CPM، تقويمات، Baseline وإصدارات، وتوزيع مخطط للكميات والقيمة. |
| تكامل | كل نشاط قابل للربط ببند BOQ، وكل WIR معتمد ينعكس على الكمية والـEV دون تجاوز نطاق العقد. |
| حوكمة | منع تجاوز كمية البند، منع تواريخ خارج العقد/البند، والتحذير الرسمي لتأخير نهاية البند عن أنشطته. |
| مصالحة | تطابق PV/EV والكميات التراكمية مع Baseline معتمدة وData Date محدد. |
| UX/استيراد | استيراد Primavera/XER أو Excel إلى Draft مع خريطة WBS/Activity/BOQ وتصحيح الأخطاء قبل الترحيل. |
| اختبارات | سيناريوهات علاقات CPM، تقويم، تأخير، WIR، Baseline، إعادة Baseline، واستيراد برنامج فعلي. |

## المرحلة C — التجاري والمالي والتكلفة

**الهدف:** دورة مضبوطة من العقد والتغيير إلى الالتزام والتكلفة والشهادة والتدفق النقدي.

| البعد | شرط 8/10 للمرحلة C |
|---|---|
| وظيفي | SOV وBudget وCommitment وPO وCost Change وPayment Certificate وCash Forecast ضمن حالات عمل واضحة. |
| تكامل | Variation معتمد ينعكس، وفق تاريخ سريانه، على BOQ/SOV/Budget/Schedule/Cash؛ شهادات العميل والباطن تؤثر في AR/AP والتدفقات. |
| حوكمة | اعتماد، احتجاز، ضريبة، دفعة مقدمة، خصومات، إقفال فترة، وReversal رسمي بدل تعديل قيود معتمدة. |
| مصالحة | قيمة العقد المعدلة، التكلفة الفعلية، الالتزامات، ETC/EAC، والشهادات والتدفقات قابلة للتتبع إلى مستند المصدر. |
| UX/استيراد | إدخال شهادة أو تكلفة يوضح مصدر السعر والكمية والتراكمات، ويمنع الترحيل الناقص أو المكرر. |
| اختبارات | سيناريو كامل: عقد → تغيير → تكلفة/التزام → شهادة → سداد → تدفق نقدي، مع حالات رفض وإقفال فترة. |

## المرحلة D — الموقع والجودة والمستندات

**الهدف:** تحويل أحداث الموقع إلى بيانات تشغيلية معتمدة مرتبطة بالوقت والتكلفة والجودة.

| البعد | شرط 8/10 للمرحلة D |
|---|---|
| وظيفي | WIR/NCR/RFI/Punch/Daily Report/Submittal/Document مع حالات عمل، مرفقات وإصدارات ومهلات. |
| تكامل | المستند أو الطلب مرتبط بالمشروع والعقد وBOQ/النشاط عند الاقتضاء، والاعتماد ينعكس فقط في المؤشرات المسموح بها. |
| حوكمة | مراجعات واعتمادات ومسؤوليات وتواريخ استحقاق وعدم حذف سجلات معتمدة؛ سجل تدقيق للمرفقات والحالات. |
| مصالحة | كل قيمة إنجاز أو جودة في التقرير قابلة للرجوع إلى WIR/قياس أو مستند محدد. |
| UX/استيراد | نماذج موقع سريعة، مرفقات واضحة، بحث/فلترة، ورسائل تصعيد قابلة للتصرف. |
| اختبارات | حالات دورة العمل، الرفض، التصعيد، فقدان المرفق، تكرار المرجع، وربط WIR بالتكلفة/الفاتورة عند الاعتماد. |

## المرحلة E — PMO والتقارير ودعم القرار

**الهدف:** تقارير موثوقة تقود من المؤشر التنفيذي إلى مصدر الرقم والإجراء المطلوب.

| البعد | شرط 8/10 للمرحلة E |
|---|---|
| وظيفي | Portfolio dashboard، تقارير دورية، S-curves، تنبيهات مبكرة، قوالب تقارير، وتحليل سيناريوهات. |
| تكامل | جميع المؤشرات تستخدم Metric Engine موحدًا وData Date/فلاتر موحدة، مع Drill-down إلى المستند والصف المصدر. |
| حوكمة | تقرير معتمد ومقفل لا يتغير دون إصدار جديد؛ يوضح تاريخ البيانات وصاحب التقرير ومصدر كل مؤشر. |
| مصالحة | PV/EV/AC/EAC/CPI/SPI/Cash والمجاميع المالية تتطابق مع البيانات المعتمدة ضمن نفس تاريخ القطع. |
| UX/استيراد | فلاتر محفوظة، عرض واضح للاستثناءات، تصدير موثوق، وقوالب مرنة دون تغيير الحسابات الأساسية. |
| اختبارات | اختبارات لفلترة التاريخ، اختلاف المشروع/العقد، Drill-down، التقرير المقفل، ومطابقة dashboard مع بيانات القبول. |

## المرحلة F — المنصة المؤسسية والتعاون

**الهدف:** تشغيل متعدد المستخدمين والمشروعات مع أمن وتدقيق وتزامن موثوقين.

| البعد | شرط 8/10 للمرحلة F |
|---|---|
| وظيفي | قاعدة مركزية وAPI ومزامنة Desktop/Web وصلاحيات ومشاركة خارجية ضمن نطاق مصرح به. |
| تكامل | نفس قواعد العمل والحسابات والاعتمادات تعمل في Desktop وWeb من مصدر بيانات واحد. |
| حوكمة | RBAC، فصل بيانات الشركات/المشروعات، Audit Trail غير قابل للتعديل للمعاملات المعتمدة، وسياسة نسخ واستعادة. |
| مصالحة | اختبار تزامن وتعارض يثبت عدم فقد أو ازدواج معاملات وأن الأرصدة والتقارير متطابقة بين القنوات. |
| UX/استيراد | تجربة متسقة للمستخدمين ذوي الصلاحيات المختلفة، مع رفض مفهوم للإجراء غير المسموح. |
| اختبارات | اختبارات API وصلاحيات وتزامن وتعافٍ وأمن أساسي، إضافة إلى قبول متعدد المستخدمين. |

## نموذج تقرير الإغلاق

لكل مرحلة، يوثق التقرير:

1. نتيجة كل بعد من ستة أبعاد مع دليل ورابط الاختبار.
2. السيناريوهات التي نُفذت والبيانات المرجعية المستخدمة.
3. أي استثناء مفتوح، مالكه، ولماذا لا يمنع الإغلاق — إن وجد.
4. نتيجة بناء الإنتاج، فحص قاعدة البيانات، وخطة/نقطة الرجوع.
5. قرار صريح: **مقبول 8/10 أو أكثر** / **غير مقبول ويعاد إلى قائمة الإصلاح**.
